## CRITICAL: GDPR Export requests are silently processed as Erasure — data destruction instead of data export
- **File**: `src/Privacy/Privacy.Application/Requests/Commands/InitiateRequest/InitiatePrivacyRequestCommand.cs:67`, `src/Contracts/Privacy/InitiatePrivacyRequestMessage.cs:3-7`, `src/Privacy/Privacy.Application/Requests/Sagas/PrivacyRequestStateMachine.cs:38,44`, `src/Contracts/Privacy/PrivacyErasureRequested.cs:3-7`, `src/Privacy/Privacy.Application/Requests/Queries/GetErasureStatus/GetErasureStatusQuery.cs:69`
- **Issue**: `InitiatePrivacyRequestCommand` accepts `PrivacyRequestType.Export` and the validator (`InitiatePrivacyRequestCommandValidator`) permits it (`RuleFor(v => v.Type).IsInEnum()`), and `PrivacyRequest.Create(userId, type)` persists it correctly. But the handler publishes `InitiatePrivacyRequestMessage { RequestId, UserId }` (`InitiatePrivacyRequestCommand.cs:67`) — this contract has **no `Type` field at all** (confirmed: `InitiatePrivacyRequestMessage.cs:3-7`). The saga's `Initially(When(RequestInitiated))` handler then unconditionally sets `context.Saga.RequestType = "Erasure";` (`PrivacyRequestStateMachine.cs:38`) and publishes `PrivacyErasureRequested` (`PrivacyRequestStateMachine.cs:44`) — a contract that also has no `Type` field (`PrivacyErasureRequested.cs:3-7`). Downstream, all three consumers (`Identity.Application/Consumers/PrivacyErasureRequestedConsumer.cs:16-96`, `Orders.Application/Consumers/PrivacyErasureRequestedConsumer.cs:13-72`, `Payments.Application/Consumers/PrivacyErasureRequestedConsumer.cs:14-70`) unconditionally anonymize/delete user data with no type branching. The `PrivacyDataExportRequested` contract (`src/Contracts/Privacy/PrivacyDataExportRequested.cs`) is defined but is never published or consumed anywhere in `src/` — dead/orphaned. `GetErasureStatusQuery.cs:69` also hardcodes `Type: PrivacyRequestType.Erasure` in the response DTO regardless of the original request type.
- **Impact**: A user submitting a GDPR Article 15 **data access/export** request (`type: "Export"`) has their account data **permanently anonymized/erased** by identity-svc, orders-svc, and payments-svc instead of exported. This is irreversible data loss triggered by the documented, validator-accepted public API contract — not a theoretical edge case.
- **Fix**: Add `PrivacyRequestType Type` to `InitiatePrivacyRequestMessage`, `PrivacyErasureRequested` (or introduce a distinct `PrivacyDataExportRequested` flow wired to real export consumers), branch the state machine's `Initially` handler on `context.Message.Type`, and add an E2E/integration test asserting `type: "Export"` does NOT trigger the erasure consumers. Until export is genuinely implemented, reject `Type == Export` at the API/validator with `501 Not Implemented` rather than silently reinterpreting it as erasure.

## CRITICAL: IDOR — Service-role callers can erase any user's data without the required scope being enforced
- **File**: `src/Privacy/Privacy.Api/Controllers/PrivacyRequestsController.cs:41-61`
- **Issue**: `if (User.IsInRole("Service") && command.UserId != Guid.Empty)` trusts the request body's `UserId` for any caller holding a "Service" role JWT. The code checks for a `privacy:erase` scope/claim but when it's absent, it only logs a warning (`"IDOR risk: ... Proceeding (enforcement pending PLATFORM-SEC-12)"`) and proceeds anyway (line 47-61) — the `// TODO: enforce privacy:erase claim` at line 40 confirms the check is decorative, not a control.
- **Impact**: Any service holding a "Service"-role token (multiple services per the platform's own architecture) — or a token obtained via a compromised/misconfigured service credential — can trigger irrecoverable data erasure for an arbitrary `UserId` with zero additional authorization. Combined with the finding above, this also means a Service-role caller can silently trigger destructive erasure while believing it requested an export.
- **Fix**: Reject the request with `403 Forbidden` when `hasEraseScope` is false instead of logging and proceeding. If claim infrastructure genuinely isn't ready, this endpoint must not accept service-initiated `UserId` overrides at all until it is.

### [HIGH]: Duplicate active PrivacyRequest race — pessimistic lock is released before the insert it's meant to protect, and no unique constraint exists to catch the race
- **File**: `src/Privacy/Privacy.Application/Requests/Commands/InitiateRequest/InitiatePrivacyRequestCommand.cs:48-50,71-83`; `src/Privacy/Privacy.Infrastructure/Persistence/PrivacyDbContext.cs:31`; `src/Privacy/Privacy.Infrastructure/Migrations/20260514014811_InitialCreate.cs`
- **Issue**: The handler calls `_context.Database.ExecuteSqlInterpolatedAsync("...FOR UPDATE SKIP LOCKED", ...)` (line 48-50) with the comment "This implements the Three-Phase Gateway Law: Phase 1 (lock + check)". No `Database.BeginTransactionAsync()` is ever called anywhere in this handler (confirmed: no transaction-wrapping `IPipelineBehavior` exists in `src/BuildingBlocks/Behaviors/` — only `LoggingBehavior`, `TelemetryBehavior`, `ValidationBehavior`). Without an explicit transaction, EF Core auto-commits the raw SQL statement in its own connection/transaction, releasing the row lock immediately — before the later `_context.SaveChangesAsync(cancellationToken)` at line 71 runs in a *separate* implicit transaction. The lock provides zero protection across the check-then-insert window. The fallback catch at line 73 (`DbUpdateException` on Postgres `23505`) is dead code: `entity.HasIndex(e => e.UserId)` (`PrivacyDbContext.cs:31`) has no `.IsUnique()`, and the InitialCreate migration creates only a non-unique `IX_PrivacyRequests_UserId` index — there is no unique constraint in the database that could ever raise `23505` for this scenario.
- **Impact**: Two concurrent `Initiate` calls for the same user (e.g. double-click, retry after timeout, or two colluding clients) can both pass the "no active request" check and both insert `PrivacyRequest` rows, each spawning an independent saga that dispatches erasure/export messages to identity-svc, orders-svc, and payments-svc concurrently — violating the intended one-active-request-per-user invariant and corrupting the GDPR audit trail (which is legally load-bearing for this service).
- **Fix**: Wrap the lock query and insert in a single `await using var tx = await _context.Database.BeginTransactionAsync(cancellationToken);` (this is an HTTP handler, not a MassTransit consumer, so this doesn't violate the MassTransit Transaction Law), and add a real unique partial index, e.g. `CREATE UNIQUE INDEX IX_PrivacyRequests_UserId_Active ON privacy."PrivacyRequests" ("UserId") WHERE "Status" IN (0,1);` so the `23505` catch clause becomes reachable as true defense-in-depth.

### [HIGH]: IdempotencyKey is never populated, making the "idempotent" command's idempotency protection a permanent no-op
- **File**: `src/Privacy/Privacy.Application/Requests/Commands/InitiateRequest/InitiatePrivacyRequestCommand.cs:14`; `src/Privacy/Privacy.Api/Controllers/PrivacyRequestsController.cs:31,63,71`
- **Issue**: `InitiatePrivacyRequestCommand` implements `IIdempotentCommand` with `IdempotencyKey = ""` as the default, and the controller binds `command` directly from the JSON body with no header/query extraction of an idempotency key (confirmed by `IdempotencyBehavior.cs`: `if (string.IsNullOrWhiteSpace(key)) return await next();` — empty keys are a complete no-op, no dedup, no journal write). - **Impact**: The command is nominally idempotent by contract but has zero working idempotency protection in practice for every real caller — it relies entirely on the broken check-then-act race described above.

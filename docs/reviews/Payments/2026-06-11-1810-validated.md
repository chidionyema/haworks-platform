## CRITICAL: Database Entity Tracking Issue

### CONFIRMED: Untracked Entities Won't Persist Changes  
**Confidence: 10/10**
- **File**: src/Payments/Payments.Application/Commands/Refunds/CreateRefundCommand.cs:27
- **Issue**: Handler fetches payment with `GetByIdAsync()` which uses `AsNoTracking()`, then calls `payment.RecordRefund()` and expects `SaveChangesAsync()` to persist changes
- **Impact**: Refund amounts won't be recorded in database, causing data consistency issues and allowing over-refunding
- **Fix**: Use `GetByIdTrackedAsync()` instead:
```csharp
var payment = await paymentRepository.GetByIdTrackedAsync(request.PaymentId, ct);
```

## HIGH Priority Issues

### CONFIRMED: Idempotency Key Anti-Pattern
**Confidence: 10/10**
- **File**: src/Payments/Payments.Api/Controllers/RefundsController.cs:25
- **Issue**: Server generates new idempotency keys instead of accepting client-provided ones
- **Impact**: Defeats idempotency protection - duplicate requests will create multiple refunds
- **Fix**: Accept idempotency key from client headers or request body:
```csharp
var idempotencyKey = Request.Headers["Idempotency-Key"].FirstOrDefault() 
    ?? body.IdempotencyKey ?? throw new BadRequestException("Idempotency-Key required");
```

### CONFIRMED: Overly Broad Exception Handling
**Confidence: 9/10**
- **File**: src/Payments/Payments.Infrastructure/Stripe/StripeWebhookProcessor.cs:284
- **Issue**: `ParseDataObject<T>()` catches ALL exceptions including system-level ones
- **Impact**: Could hide critical failures like OutOfMemory or ThreadAbort exceptions
- **Fix**: Catch specific exceptions:
```csharp
catch (JsonException ex)
{
    _logger.LogWarning(ex, "Failed to parse JSON for type {Type}", typeof(T).Name);
    return null;
}
catch (KeyNotFoundException ex)
{
    _logger.LogWarning(ex, "Missing required JSON property for type {Type}", typeof(T).Name);
    return null;
}
```

## CRITICAL: EasyPost webhook has no signature verification — fully spoofable
- **File**: `src/Shipping/Shipping.Api/Controllers/ShipmentsController.cs:97-134` (`HandleWebhook`, `[AllowAnonymous]`)
- **Issue**: `grep -rin "hmac|signature|WebhookSecret" src/Shipping --include="*.cs"` returns nothing. Compare `src/Payments/Payments.Api/Webhooks/StripeSignatureValidator.cs`, which exists specifically to prevent this. The handler trusts `[FromBody] EasyPostWebhookPayload` with zero auth.
- **Impact**: Anyone can `POST /api/v1/Shipments/webhooks/easypost` with `{"Description":"tracker.updated","Result":{"TrackingCode":"<guessed>","Status":"delivered"}}`. Tracking numbers are discoverable via the IDOR below (`GetByOrder`/`GetShipment`), so an attacker can forge `Delivered` on someone else's shipment, publishing a fabricated `ShipmentDeliveredEvent` that downstream consumers (order completion, notifications) will treat as real.
- **Fix**: Validate EasyPost's `X-Hmac-Signature` header against a webhook secret before processing, mirroring `StripeSignatureValidator`.

## CRITICAL: IDOR — no ownership check on shipment endpoints
- **File**: `src/Shipping/Shipping.Api/Controllers/ShipmentsController.cs:44` (`BuyLabel`), `:75` (`GetShipment`), `:83` (`GetByOrder`)
- **Issue**: All three are `[Authorize]` (any authenticated user) but look up by `Id`/`OrderId` alone — no check that the caller owns the order.
- **Impact**: `BuyLabel` is the worst: any logged-in user can `POST /{anyGuid}/buy` for a shipment that isn't theirs, spending real EasyPost account funds and generating a label/tracking for someone else's order. `GetShipment`/`GetByOrder` leak another customer's full ship-to/ship-from address and tracking info.
- **Fix**: Load the parent order (or embed `UserId`) and enforce `shipment.OrderId` belongs to the authenticated principal (or require a service-role claim if this is meant to be internal-only, in which case drop `[Authorize]` in favor of a service policy).

## HIGH: BuyLabel violates the Three-Phase Gateway law — double-purchase race
- **File**: `src/Shipping/Shipping.Api/Controllers/ShipmentsController.cs:44-61`; `src/Shipping/Shipping.Api/Domain/Shipment.cs` `MarkLabelPurchased` (no status guard)
- **Issue**: No Phase-1 "Pending" transition/lock before the external `BuyLabelAsync` call, and `MarkLabelPurchased` doesn't check `shipment.Status` before overwriting.
- **Impact**: Two concurrent/retried `/buy` calls for the same shipment both call EasyPost's `Buy()` independently — two labels purchased, two charges — before either write hits the DB. A double-click, client retry, or duplicate BFF forward all trigger this.
- **Fix**: Per CLAUDE.md Law #2: Phase 1 lock the row (`FOR UPDATE`) and set `Status = Pending/Buying`, commit; Phase 2 call EasyPost; Phase 3 re-lock, guard `if (shipment.Status != Pending) return Conflict()`, then finalize.

## HIGH: No resilience (Polly) around EasyPost calls
- **File**: `src/Shipping/Shipping.Api/Shipping.Api.csproj` (no Polly package reference, confirmed via `grep`); `src/Shipping/Shipping.Api/Infrastructure/EasyPostShippingProvider.cs` (all three methods call the SDK bare)
- **Issue**: CLAUDE.md Law #2 mandates external I/O be wrapped in Polly resilience policies. This service has zero.
- **Impact**: Any transient EasyPost network blip fails the whole HTTP request (including `BuyLabel`, where a failure after a partial remote purchase leaves state unreconciled).
- **Fix**: Add `Microsoft.Extensions.Http.Resilience` (already used elsewhere in the platform per `Payments`) with retry+circuit-breaker around the `Client` calls.

## HIGH: No idempotency key sent to EasyPost
- **File**: `src/Shipping/Shipping.Api/Infrastructure/EasyPostShippingProvider.cs:24-46` (`Create`), `:68-77` (`Buy`)
- **Issue**: `grep -rin "Idempotency" src/Shipping` returns nothing. Neither the shipment-create nor the label-buy call passes an idempotency key to EasyPost.
- **Impact**: Once retries are added (Polly above, or client retries on timeout), a retried `Buy()` call has no way to be recognized as a duplicate by EasyPost — double label purchase / double charge.

## HIGH: Silent fallback to `LowestRate()` masks tampered/stale rate IDs
- **File**: `src/Shipping/Shipping.Api/Infrastructure/EasyPostShippingProvider.cs:70-71`
```csharp
var rate = shipment.Rates?.FirstOrDefault(r => string.Equals(r.Id, rateId, StringComparison.Ordinal))
    ?? shipment.LowestRate();
```
- **Issue**: If the client-supplied `rateId` doesn't match any rate on the shipment (stale UI state, tampered request, bug), the code silently buys the *cheapest* rate instead of returning an error.
- **Impact**: Customer sees/agrees to one price/carrier in the UI, backend silently buys a different one — price/carrier mismatch with no error surfaced to caller or logs.
- **Fix**: `if (rate == null) return BadRequest("Unknown rate id");` — never fall through to a different rate implicitly.

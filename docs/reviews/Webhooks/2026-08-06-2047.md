## CRITICAL: SSRF via DNS-rebinding bypass in webhook URL validation
- **File**: `src/Webhooks/Webhooks.Application/Subscriptions/SubscriptionValidators.cs:30,45,101` + `src/Webhooks/Webhooks.Application/Subscriptions/SubscriptionHandlers.cs:96-111`
- **Issue**: `IsPrivateIp(uri.Host)` (line 45) only fires when `System.Net.IPAddress.TryParse(host, ...)` succeeds — i.e. only when the attacker literally puts an IP in the URL. Any hostname (`https://attacker-controlled.example`) skips this check entirely because DNS is never resolved during validation. `ValidateWebhookUrlAsync` (`SubscriptionHandlers.cs:96`) then makes a **live outbound POST from the Webhooks service itself** to that URL via `httpFactory.CreateClient("WebhookValidator")`.
- **Impact**: Any authenticated caller can register a domain they control DNS for, point it at an internal Fly `*.internal` service, `169.254.169.254`, or any RFC1918 address, and the platform's own backend will issue a real HTTP(S) request to it during `Create`. `AllowAutoRedirect = false` blocks redirect-based SSRF but does nothing against DNS rebinding. Only the "HTTPS only" rule offers partial mitigation (blocks plain-HTTP metadata endpoints), but any internal service terminating TLS is reachable. This is a server-side request forgery primitive against internal infrastructure, reachable by any authenticated user, not just partners.
- **Fix**: Resolve the hostname (`Dns.GetHostAddressesAsync`) before making the validation request, run `IsPrivateIp` against **every resolved address**, and pin the `HttpClientHandler`'s `ConnectCallback` to the pre-validated IP (so a second DNS lookup at connect time can't rebind to a different address). Reject if any resolved address is private/link-local/loopback/multicast.

### HIGH: Webhook secret is never returned to the caller — feature is unusable as built
- **File**: `src/Webhooks/Webhooks.Application/Subscriptions/SubscriptionHandlers.cs:23-47` (Create returns `Result.Success(sub.Id)`), `:72-85` (Rotate returns only `secret[0..8] + "..."`)
- **Issue**: When `request.Secret` is null, a secret is generated server-side (`Guid.NewGuid().ToString("N")`, line ~30) and stored, but `Create` returns only the subscription `Guid` — the generated secret is discarded and never surfaced. `RotateSecret` returns a truncated 8-char preview (`secretHash` masking at line 84), never the full value.
- **Impact**: If a partner doesn't supply their own secret, they have no way to ever retrieve it — `GetWebhookSubscriptionQuery` only exposes `SecretPreview` (last 4 chars, `SubscriptionHandlers.cs:107`). Whatever consumer is meant to use `Secret` for HMAC verification can never be configured correctly for the common "let the server generate it" path.
- **Fix**: Either return the full secret exactly once at creation/rotation time (standard practice for API keys — never store/retrieve again), or remove the fields if truly dead (see next finding).

### HIGH: `Secret`/`SecretHash` are dead fields that store plaintext secrets unnecessarily
- **File**: `src/Webhooks/Webhooks.Domain/WebhookSubscription.cs:9-11`, `src/Webhooks/Webhooks.Infrastructure/Svix/SvixWebhookForwarder.cs:1-45`
- **Issue**: Class docs on `IWebhookDispatcher` and `SvixWebhookForwarder` both state "Svix handles retry, signing, delivery tracking, and SSRF protection." `SvixWebhookForwarder.ForwardAsync` never reads `sub.Secret` or `sub.SecretHash` — Svix generates and manages its own per-endpoint signing secrets. Combined with the previous finding (secret unrecoverable), nothing in the reviewed code path consumes `Secret`/`SecretHash` for anything.
- **Impact**: A plaintext webhook secret (`Secret` column, `WebhooksDbContext.cs`, `HasMaxLength(200)`) is persisted for every subscription with no functional purpose — pure at-rest exposure risk if the DB is ever breached, for a value that doesn't even work end-to-end (finding above).
- **Fix**: Confirm with product whether `Secret` is genuinely dead. If so, drop the columns in a migration. If it's meant to be used (e.g., for the platform's own signature verification bypassing Svix), wire it up and fix the return-value gap above.

### HIGH: No endpoint to list a partner's own subscriptions
- **File**: `src/Webhooks/Webhooks.Application/Common/PagedResult.cs:3`, `src/Webhooks/Webhooks.Api/Controllers/SubscriptionsController.cs` (no list action), `src/Webhooks/Webhooks.Application/Subscriptions/SubscriptionCommands.cs` (no `ListWebhookSubscriptionsQuery`)
- **Issue**: `PagedResult<T>` exists specifically for a paginated list response but is referenced nowhere else in the service (`grep -rn PagedResult src/Webhooks` returns only its own declaration). There is no `GET /api/v1/webhooks/subscriptions` (list) endpoint — only `GET .../{id:guid}`.
- **Impact**: A partner who loses the `Guid` returned from `Create` has no way to discover it again through the API; they must have persisted it client-side. Given up to 50 subscriptions per partner (`SubscriptionValidators.cs:39`), self-service management is effectively impossible without direct DB access.
- **Fix**: Implement `ListWebhookSubscriptionsQuery` + `GET` action returning `PagedResult<WebhookSubscriptionDto>` filtered by `CallerPartnerId`.

## CRITICAL: Migration creates tables with no corresponding domain entity/DbSet
- **File**: `src/Webhooks/Webhooks.Infrastructure/Persistence/Migrations/20260516105727_InitialCreate.cs` (creates `webhook_deliveries`, `webhook_delivery_attempts`), `src/Webhooks/Webhooks.Infrastructure/Persistence/WebhooksDbContext.cs:9` (only `DbSet<WebhookSubscription> Subscriptions`)
- **Issue**: The migration creates `webhook_deliveries` (with `Status`, `NextAttemptAt`, `Attempts`, `xmin` rowversion) and `webhook_delivery_attempts` tables, complete with FKs and partial indexes, but no `WebhookDelivery`/`WebhookDeliveryAttempt` entity or `DbSet` exists anywhere in `Webhooks.Domain` or `WebhooksDbContext`.
- **Impact**: These tables are unreachable dead schema in production — they will never be populated (dispatch/retry tracking is fully delegated to Svix per the architecture). At best this is stale scaffolding from a pre-Svix design; at worst it signals the model and migrations have drifted, which is exactly the class of bug `check-migration-drift.sh` (per project memory) is meant to catch, but it only detects the opposite direction (model without migration), not migration without model.
- **Fix**: Either delete the unused tables via a follow-up migration, or confirm they're intentionally reserved and document why (e.g., a Svix-independent audit trail planned for later).

### MEDIUM: TOCTOU race on the 50-subscriptions-per-partner limit
- **File**: `src/Webhooks/Webhooks.Application/Subscriptions/SubscriptionValidators.cs:36-40`
- **Issue**: The limit is enforced via `CountAsync` inside `MustAsync`, then `Create` inserts unconditionally. No unique constraint, advisory lock, or serializable transaction backs this.
- **Impact**: Concurrent `Create` calls near the boundary can push a partner past 50 subscriptions (check-then-act race, lens #2).
- **Fix**: Enforce with a DB-level check constraint via trigger, or take a row lock on a per-partner counter row before insert, per the platform's pessimistic-locking convention (`FOR UPDATE`).

### MEDIUM: No role/policy restriction — any authenticated user can register webhooks
- **File**: `src/Webhooks/Webhooks.Api/Controllers/SubscriptionsController.cs:14,17-20`
- **Issue**: `GetPartnerId()` reads `partner_id` claim, falling back to `ClaimTypes.NameIdentifier` (the generic user id) if `partner_id` is absent. The controller carries a bare `[Authorize]` with no `Roles=`/`Policy=` restricting access to actual partner accounts.
- **Impact**: If `partner_id` is only issued to a subset of users, every other authenticated user (e.g. ordinary customers) can still successfully call every action in this controller, using their own user id as an ad-hoc "partner id." This may be intentional, but nothing in the code enforces it as a decision — worth confirming against the intended authorization model.
- **Fix**: If webhook subscriptions are partner-only, add `[Authorize(Roles = "Partner")]` (or equivalent policy) and drop the `NameIdentifier` fallback so partner_id absence returns 403, not a silently-substituted identity.

### MEDIUM: `Svix:AuthToken` fails silently instead of fast
- **File**: `src/Webhooks/Webhooks.Infrastructure/DependencyInjection.cs:36-38`
- **Issue**: `Svix:ServerUrl` throws `InvalidOperationException` if missing (line 37), but `Svix:AuthToken` on line 38 falls back to `""` — despite the comment immediately above stating both "MUST be provided."
- **Impact**: A misconfigured deployment starts up healthy, then every `SvixWebhookForwarder.ForwardAsync` call fails with a 401 at runtime, discovered only when the first webhook fan-out happens (or worse, silently swallowed if callers don't handle the exception — see `EventFanOutConsumer.FanOutAsync`, which has no try/catch around `dispatcher.ForwardAsync`, so the whole consume fails and retries indefinitely without a health check ever going red).
- **Fix**: Throw the same way `ServerUrl` does if `Svix:AuthToken` is empty.

### MEDIUM: No length validation on rotate-secret input before DB write
- **File**: `src/Webhooks/Webhooks.Application/Subscriptions/RotateWebhookSubscriptionSecretCommandValidator.cs:9-11`, `WebhooksDbContext.cs` (`Secret` column `HasMaxLength(200)`)
- **Issue**: The validator only checks `Id.NotEmpty()`; `Secret` has no `MaximumLength` rule, unlike `Url` in the other validators.
- **Impact**: A caller supplying a secret > 200 chars gets an unhandled Postgres "value too long for type character varying(200)" exception surfacing as an unhandled 500 instead of a clean validation error.
- **Fix**: Add `RuleFor(x => x.Secret).MaximumLength(200).When(x => x.Secret != null);`.

### LOW: Blocking BCrypt hashing inside async request handlers
- **File**: `src/Webhooks/Webhooks.Application/Subscriptions/SubscriptionHandlers.cs:31,76`
- **Issue**: `BCrypt.Net.BCrypt.HashPassword(secret)` runs synchronously on the request thread inside `async` handlers.
- **Impact**: Ties up a thread-pool thread for the duration of the (CPU-bound) hash computation on every create/rotate call; minor under normal load, but worth `Task.Run`-wrapping if this handler ever becomes hot.
- **Fix**: `await Task.Run(() => BCrypt.Net.BCrypt.HashPassword(secret), ct)` or move to a background-safe hashing call if the library offers one.

### LOW: `[HttpPatch]` requires a full payload, not a partial update

- **Issue**: `Update` is mapped to `PATCH` but the bound `UpdateWebhookSubscriptionCommand` requires `Url` and `Events` to be non-empty (`UpdateWebhookSubscriptionValidator`), i.e. it's a full replace, not a partial patch.

## Summary

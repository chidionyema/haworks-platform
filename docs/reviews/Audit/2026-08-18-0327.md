## CRITICAL: In-memory Channel writer permanently dies on any non-PostgresException DB failure
- **File**: src/Audit/Audit.Infrastructure/Persistence/AuditWriter.cs:107 (`catch (PostgresException ex)` in `WriteBatchAsync`), and `ProcessBatchAsync` lines 62-86
- **Issue**: `WriteBatchAsync`'s try/catch only catches `PostgresException` (a server-returned SQL error). `connection.OpenAsync()` failures — connection refused, DNS failure, pool exhaustion, transient network blip — throw the base `NpgsqlException`, not `PostgresException`, so they are NOT caught here. That exception bubbles into `ProcessBatchAsync`'s outer `catch (Exception ex) { _logger.LogError(...) }`, which just logs and falls through to the `finally` block. The `finally` block immediately tries to drain the channel and calls `WriteBatchAsync` again with the SAME failure mode (no try/catch around that call) — so the same unhandled exception type propagates straight out of `ProcessBatchAsync`, which is the body of `_workerTask = Task.Run(ProcessBatchAsync)`. The task faults and exits. No restart logic exists.
- **Impact**: One transient Postgres connectivity blip permanently stops all audit capture for the remaining life of the process — every subsequent `IAuditWriter.WriteAsync` call still succeeds (it just enqueues into the unbounded channel) with nothing ever draining it. Silent, total audit-trail outage until a manual restart; no alert fires beyond a single log line.
- **Fix**: Catch `NpgsqlException` (base type) in `WriteBatchAsync`, not just `PostgresException`. Wrap the `finally`-block retry-drain in its own try/catch. Add a supervisory restart (`Task.Run` loop that re-spawns the worker on fault) or a health check that reflects worker liveness.

## CRITICAL: Unique-constraint violation drops the entire batch, including innocent rows
- **File**: src/Audit/Audit.Infrastructure/Persistence/AuditWriter.cs:157-179 (`catch (PostgresException ex)` block in `WriteBatchAsync`)
- **Issue**: On a `PostgresException` (e.g. the per-partition unique index on `message_id` rejecting a redelivered/duplicate message), the code requeues the **entire original `batch`** unchanged — including up to 49 legitimate, non-duplicate rows that had nothing to do with the conflict. Because the offending row's `message_id` is unchanged, it will conflict identically on every retry. After `MaxRetries` (3) attempts, the whole batch — legitimate rows included — is permanently dropped via `_logger.LogError` with no further recovery.
- **Impact**: A single duplicate/redelivered message (a routine occurrence with at-least-once messaging) silently deletes up to 49 unrelated, legitimate audit events from the append-only audit trail. This directly violates the core guarantee of an audit service.
- **Fix**: On unique-violation, fall back to per-row insert with `ON CONFLICT (...) DO NOTHING` (or a targeted retry that excludes the specific conflicting `message_id` rather than the whole batch) instead of blindly requeueing the full batch.

## CRITICAL: Message ack is decoupled from durable persistence (channel is not crash-safe)
- **File**: src/Audit/Audit.Application/Capture/AuditConsumer.cs:66 (`await _writer.WriteAsync(finalRow, context.CancellationToken)`), src/Audit/Audit.Infrastructure/Persistence/AuditWriter.cs:33-36 (`WriteAsync` just does `_channel.Writer.WriteAsync(...)`)
- **Issue**: `AuditConsumer.Consume` returns as soon as the row is enqueued into an unbounded in-memory `Channel`, not after it's durably written (COPY-committed to Postgres, batched every 200ms/50 rows). MassTransit acks/removes the RabbitMQ message the moment `Consume` returns successfully. `Program.cs:41` configures `AddEntityFrameworkOutbox<AuditDbContext>` for outbound publish reliability, but `AuditConsumer` never calls `SaveChangesAsync`, so that outbox provides no protection for this write path.
- **Impact**: A process crash (OOM kill, pod eviction, deploy) between message-ack and the next batch flush permanently loses the buffered audit event — the source message is already gone from RabbitMQ, so there is no redelivery or recovery path. For an audit trail whose entire purpose is not losing data, this is a foundational integrity gap.
- **Fix**: Either persist via the ambient consumer transaction (call `SaveChangesAsync` inside `Consume`, so MassTransit's inbox/outbox ties ack to commit), or accept the batching design but bound the risk explicitly (e.g., synchronous flush for a configurable subset, or a WAL-backed queue instead of an in-memory `Channel`), and document the trade-off.

## HIGH: Unvalidated `limit` query param crashes `ListEvents` for any `limit <= 0`
- **File**: src/Audit/Audit.Api/Controllers/AuditQueryController.cs:31 (`[FromQuery] int limit = 50`), src/Audit/Audit.Infrastructure/Queries/AuditQueryService.cs:41-46
- **Issue**: No `[Range]`/validation on `limit`. `AuditQueryService.ListAsync` does `.Take(request.Limit + 1)`, then `if (items.Count > request.Limit) { var last = items[request.Limit - 1]; ... }`. For `limit=0`, `Take(1)` returns up to 1 row; `1 > 0` is true, so `items[0 - 1]` = `items[-1]` throws `ArgumentOutOfRangeException`. For any `limit < 0`, `Take(limit+1)` clamps effectively to 0 rows, but `items.Count(0) > request.Limit(negative)` is still true, so it crashes unconditionally regardless of data present.
- **Impact**: `GET /audit/events?limit=0` (or any negative value), from any authenticated `audit-reader`, reliably throws an unhandled exception → 500. No upper bound either, so a large `limit` triggers an unbounded DB read.
- **Fix**: `[Range(1, 500)] int limit = 50` on the controller parameter, and defensively clamp/guard in `AuditQueryService` before indexing.

## HIGH: Export job can be processed twice — check-then-act race with no row lock
- **File**: src/Audit/Audit.Infrastructure/Export/AuditExportWorker.cs:57-64 (`ProcessJobAsync` check-then-act on `Status`), lines 100-105 (`strandedJobIds` query picks up ALL `Queued` jobs, not just genuinely stalled ones, every 1 minute)
- **Issue**: `PollStrandedJobsAsync` runs every 60s and unconditionally reprocesses every job currently in `Queued` state — not just ones stuck past the 10-minute stall window. A job enqueued via `EnqueueAsync` is picked up by the channel-driven `ExecuteAsync` loop *and* can be concurrently picked up by this poll loop before the channel consumer marks it `Running`. Both call `ProcessJobAsync`, which does `if (job.Status != Queued) return;` then sets `Running` and saves — a classic check-then-act race with no `FOR UPDATE`/optimistic concurrency token (violates the platform's own idempotency law).
- **Impact**: Duplicate CSV generation and duplicate S3 uploads for the same export job; wasted resources and confusing duplicate work under load, worse if it races on the same temp file naming path or the job row itself.
- **Fix**: Use `FOR UPDATE SKIP LOCKED` (or a lease/claim column) when transitioning `Queued → Running`, per the platform's Logical Idempotency Law.

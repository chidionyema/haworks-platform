# Code Review: src/Scheduler

## CRITICAL: `VaultLeases`/`RotationAuditEntries` tables are never created — no migration exists
- **File**: `src/Scheduler/Scheduler.Infrastructure/Persistence/SchedulerDbContext.cs:12-13`
- **Issue**: `SchedulerDbContext` declares `DbSet<VaultLease>` and `DbSet<RotationAuditEntry>` with full fluent config (unique index on ServiceName/RoleName/CredentialType, secondary index on Status/ExpiresAt). Verified on disk: the Migrations folder contains exactly one migration, `20260513080006_InitialCreate.cs`, which only creates `InboxState`/`OutboxState`/`OutboxMessage`. `SchedulerDbContextModelSnapshot.cs` confirms this — its `BuildModel` body is empty (no entities at all, not even Inbox/Outbox), meaning the tracked model snapshot is stale/out of sync with the current `OnModelCreating`.
- **Impact**: `app.MigrateDatabase<SchedulerDbContext>()` (`Program.cs:44`) only applies migrations that exist — it calls `db.Database.MigrateAsync()` (`DatabaseMigrationExtensions.cs:23`), which will not create `scheduler."VaultLeases"`. The very first query against it, `LeaseBootstrapStartupTask.StartAsync` → `repo.LeaseExistsAsync(...)` (`LeaseBootstrapStartupTask.cs:56`), throws `Npgsql.PostgresException: 42P01 relation "scheduler.VaultLeases" does not exist`. Since this throws from `IHostedService.StartAsync`, host startup aborts — the entire Scheduler service fails to boot. The whole rotation subsystem (`LeaseWatcherJob`, `LeaseRepository`) is unreachable code in production as currently migrated.
- **Fix**: Generate the missing migration (`dotnet ef migrations add AddVaultLeaseAndRotationAuditEntry --project src/Scheduler/Scheduler.Infrastructure`) and verify `dotnet ef migrations has-pending-model-changes` returns clean. Flip `scripts/check-migration-drift.sh` to strict for this service once fixed — it's currently warn-only per the platform's own drift tracker, which is exactly how this shipped unnoticed.

## CRITICAL: `RotateJwtKeyJob` is not safe to retry — a transient failure after step 4 permanently loses the real "previous" JWT key
- **File**: `src/Scheduler/Scheduler.Application/Jobs/RotateJwtKeyJob.cs:43-99`
- **Issue**: The job is annotated `[AutomaticRetry(Attempts = 3)]` (line 43) but performs an ordered, non-idempotent multi-step Vault mutation with no idempotency guard: (1) read `identity/jwt` as "current", (2) copy it to `identity/jwt-previous`, (3) generate a brand-new RSA key, (4) overwrite `identity/jwt` with it, (5) publish, (6) schedule cleanup. If step 5 or 6 throws (e.g. RabbitMQ transient outage) *after* step 4 already committed, Hangfire retries `RunAsync` from the top. On retry, step 1 now reads the *new* key (written by the failed attempt) as "current", and step 2 overwrites `jwt-previous` with it — permanently destroying the true original key that was never actually finished rotating out.
- **Impact**: Any JWT signed with the original key (issued before rotation started) becomes unverifiable the moment the retry completes, since neither `identity/jwt` nor `identity/jwt-previous` holds it anymore. This invalidates active sessions platform-wide on a benign transient RabbitMQ hiccup — this is exactly the "Logical Idempotency Law" violation the platform's own architecture rules call out (mission-critical, retry-unsafe multi-step mutation with no dedup guard).
- **Fix**: Make the job idempotent — e.g. record `rotationId`/state in a durable row before step 2, and on retry check whether a rotation is already in-flight (skip straight to re-publish/re-schedule) instead of re-reading Vault's current value as ground truth. Alternatively wrap steps 1-4 as a single "commit once" phase guarded by a rotation marker.

## CRITICAL: `SchedulingController.Schedule` lets any authenticated user publish to an arbitrary exchange/routing key on the internal bus
- **File**: `src/Scheduler/Scheduler.Api/Controllers/SchedulingController.cs:10` (`[Authorize]`, no roles/policy)
- **Issue**: `[Authorize]` with no policy requires only a valid JWT — `AddPlatformAuthentication` (`src/BuildingBlocks/Extensions/AuthenticationExtensions.cs:14-22`) wires JWKS validation only, no default role policy. `ScheduleEventCommandValidator` (`ScheduleEventCommand.cs:32-33`) only checks `TargetExchange`/`RoutingKey` are `NotEmpty()` — no allowlist. `EventPublisherJob` (`EventPublisherJob.cs:22-33`) only checks a character-safety regex, not a legitimate-exchange allowlist. The codebase elsewhere clearly has role-based gating available and used (`HangfireLocalRequestFilter.Authorize` checks `User.IsInRole("admin")`), so this is an inconsistency, not a deliberate design choice.
- **Impact**: Any principal holding a valid customer JWT can call `POST /api/v1/Scheduling/schedule` with any `TargetExchange`/`RoutingKey`/`Payload` and get it delivered onto the internal RabbitMQ topology up to a year later — a message-injection / spoofing vector into other bounded contexts' queues.
- **Fix**: Restrict to a service-role policy (`[Authorize(Roles = "Service")]` or equivalent), and/or validate `TargetExchange` against a configured allowlist of exchanges this service is permitted to target.

## HIGH: Idempotency is advertised but not implemented — duplicate submissions create duplicate scheduled jobs
- **File**: `src/Scheduler/Scheduler.Application/Scheduling/Commands/ScheduleEvent/ScheduleEventCommand.cs:81`, `src/Scheduler/Scheduler.Domain/Entities/ScheduledEvent.cs`, `SchedulerDbContext.cs` (no `DbSet<ScheduledEvent>`)
- **Issue**: `ScheduleEventCommandHandler.Handle` hardcodes `AlreadyExisted: false` (line 81) and never checks for an existing job with the same `IdempotencyKey` before calling `_scheduler.ScheduleEventAsync`, which always creates a new Hangfire job (`HangfireEventScheduler.cs`, `_backgroundJobClient.Schedule<EventPublisherJob>`). The `ScheduledEvent` domain entity — which literally has an `IdempotencyKey` property and a `Create` factory — is never persisted anywhere; `SchedulerDbContext` has no `DbSet<ScheduledEvent>` and no migration for it. It's dead code that gives the false impression dedup exists.
- **Impact**: Two API calls with the same `IdempotencyKey` (e.g. client retry after a timeout) schedule two independent Hangfire jobs, each of which will publish the event separately — duplicate downstream side effects.
- **Confirms via test gap**: `tests/Scheduler/Scheduler.Unit/ScheduleEventCommandHandlerTests.cs:56-81` (`Handle_same_idempotency_key_returns_same_job_id`) is tautological — the mock is set up to `ReturnsAsync("job-dedup")` unconditionally for that key, so both calls return `"job-dedup"` regardless of how many times `ScheduleEventAsync` was actually invoked underneath. It would still pass even with today's broken behavior (two real Hangfire jobs created).
- **Fix**: Persist `ScheduledEvent` keyed by `IdempotencyKey` (with a migration + unique index), have the handler look it up first and return the existing `JobId`/`AlreadyExisted: true` on a hit, and rewrite the test to assert `IBackgroundJobClient.Schedule` was called exactly once across both requests.

## HIGH: `EventPublisherJob` publishes without a deterministic MessageId — retries duplicate messages under a different id
- **File**: `src/Scheduler/Scheduler.Infrastructure/Messaging/EventPublisherJob.cs:56-60`
- **Issue**: `endpoint.Send<object>(envelope, ctx => { ctx.Headers.Set(...) }, ct)` never sets `ctx.MessageId`. `EventPublisherJob.PublishAsync` has no `[AutomaticRetry]` override, so Hangfire's global default (`Attempts = 10`) applies. If the RabbitMQ send succeeds but the job fails to be marked complete (crash/timeout right after), Hangfire retries `PublishAsync`, and MassTransit auto-generates a *new* random `MessageId` each time.
- **Impact**: Any downstream consumer relying on MassTransit's EF Inbox for message-level dedup (the platform's own stated idempotency mechanism) will not recognize the retry as a duplicate, since the `MessageId` differs each attempt — duplicate business-side effects for scheduled events despite the audit payload already carrying a stable `__idempotencyKey` (`HangfireEventScheduler.cs`, `EnrichPayloadWithAudit`) that's never wired into the message envelope.
- **Fix**: Derive a deterministic `ctx.MessageId` (e.g. a GUID derived from `__idempotencyKey`) so retries of the same Hangfire job produce the same MassTransit MessageId.

## HIGH: `LeaseBootstrapStartupTask` has an unguarded check-then-act race that crashes the app on concurrent startup
- **File**: `src/Scheduler/Scheduler.Api/Infrastructure/LeaseBootstrapStartupTask.cs:48-79`
- **Issue**: For each of 17 static service definitions, `StartAsync` does `LeaseExistsAsync` (line 56) then, if false, `AddLeaseAsync` (line 62), batching a single `SaveChangesAsync` (line 68) at the end — classic check-then-act with no locking, in direct violation of the platform's own "Logical Idempotency Law" (never rely on catching the resulting unique-index violation; the code here doesn't even catch it). There is a unique index on `(ServiceName, RoleName, CredentialType)` (`SchedulerDbContext.cs`), so if two instances run `StartAsync` concurrently (a normal occurrence during a rolling deploy or when scaled to 2+ machines), both pass the `exists` check for the same row, both insert, and the second `SaveChangesAsync` throws an uncaught `DbUpdateException`.
- **Impact**: Exceptions thrown from `IHostedService.StartAsync` abort host startup — the second instance (or both, depending on timing) crashes on boot instead of just skipping the already-seeded row.
- **Fix**: Catch the unique-violation case around the batched `SaveChangesAsync` and treat it as "already seeded" (log + continue), or seed via a single idempotent upsert statement instead of 17 check-then-insert round trips.

## MEDIUM: Exchange/routing-key format is validated only at Hangfire execution time, not at API input time
- **File**: `src/Scheduler/Scheduler.Application/Scheduling/Commands/ScheduleEvent/ScheduleEventCommand.cs:32-33` vs `EventPublisherJob.cs:29-38`
- **Issue**: The command validator only checks `NotEmpty()` on `TargetExchange`/`RoutingKey`. The `SafeNamePattern` character-allowlist check lives solely in `EventPublisherJob.PublishAsync`, which doesn't run until the Hangfire-scheduled time (up to 1 year later, per the `ScheduledTime` validator).
- **Impact**: A client gets `202 Accepted` for input that will deterministically fail once the job actually executes, and Hangfire will exhaust retries and mark it permanently `Failed` with no visible signal to the original caller.
- **Fix**: Move the `SafeNamePattern` check into `ScheduleEventCommandValidator` so bad input is rejected synchronously with `400 Bad Request`.

## MEDIUM: `GetActiveLeasesNeedingRotationAsync` orders purely by `ExpiresAt`, risking starvation of long-TTL leases
- **File**: `src/Scheduler/Scheduler.Infrastructure/Persistence/LeaseRepository.cs:13-20`
- **Issue**: `OrderBy(l => l.ExpiresAt).Take(batchSize)` then filters `NeedsRotation()` in memory. Leases mix 24h (database) and 720h (PKI) TTLs. A PKI lease already past its 80% threshold (576h elapsed of 720h) can still have an `ExpiresAt` further in the future than dozens of fresh 24h database leases, so it can be pushed out of the `Take(50)` window by leases that don't actually need rotation yet.
- **Impact**: Currently latent — only 17 rows are ever seeded (`LeaseBootstrapStartupTask.ServiceDefinitions`), well under `BatchSize = 50` — but becomes a real bug the moment the lease population grows past the batch size.
- **Fix**: Order by (or filter on) rotation urgency (elapsed/total-TTL ratio) rather than raw `ExpiresAt`, or compute `NeedsRotation` in the SQL predicate instead of taking a fixed page first.

## LOW: Concurrency exception matched by string type name instead of a typed catch
- **File**: `src/Scheduler/Scheduler.Application/Jobs/LeaseWatcherJob.cs:76`
- **Issue**: `catch (Exception ex) when (string.Equals(ex.GetType().Name, "DbUpdateConcurrencyException", StringComparison.Ordinal))` — presumably to avoid an EF Core dependency in the Application layer, but this is fragile: it won't match if the exception is wrapped (e.g. inside an `AggregateException`) and silently lets a real concurrency conflict propagate as an unhandled job failure instead of the intended graceful "another instance handled it" path.
- **Fix**: Define a small marker exception (e.g. `LeaseConcurrencyConflictException`) thrown by `ILeaseRepository.SaveChangesAsync`, translated from the EF exception at the Infrastructure boundary, and catch that concrete type here.

## LOW: Hangfire dashboard is unavailable in production, with no alternative visibility into failed jobs

- **Issue**: `app.UseHangfireDashboard` is gated entirely behind `app.Environment.IsDevelopment()`. In production there is no dashboard and no `HangfireLocalRequestFilter`-equivalent auth path to view it, so operators have no way to inspect stuck/failed recurring jobs (e.g. the exhausted-retry `EventPublisherJob` failures noted above) short of log-diving.

## Summary
- **Findings**: 3 CRITICAL, 3 HIGH, 2 MEDIUM, 2 LOW (10 total)
- **Top 3 most urgent**:
  1. `VaultLeases`/`RotationAuditEntries` tables have no migration — the service cannot start against a real database as currently shipped.
  2. `RotateJwtKeyJob`'s retry-on-transient-failure path can permanently destroy the previous JWT key, invalidating live sessions platform-wide.
  3. `SchedulingController` allows any authenticated user to inject arbitrary messages onto the internal bus — no role/exchange allowlist.
- **Overall service health rating: 3/10.** The design intent (outbox-safe consumers, three-phase Vault rotation, idempotency-key field, DisableConcurrentExecution locks) is sound and mostly well-documented in comments, but a core piece of persistence (the lease tables) appears to have never been migrated, and two of the platform's own mandatory laws (retry-safety, logical idempotency) are violated in exactly the places CLAUDE.md calls out as mandatory. This needs the migration fix verified against a real Postgres instance before this service can be considered deployable.

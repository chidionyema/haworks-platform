## CRITICAL: Fraud detection rule internals disclosed to any authenticated user (IDOR / info disclosure)
- **File**: src/RulesEngine/RulesEngine.Api/Controllers/RulesController.cs:35-51
- **Issue**: `List` (`GET /api/v1/rules`) and `Get` (`GET /api/v1/rules/{id}`) carry only `[Authorize]` from the class level. Create/Update/Delete are `[Authorize(Roles = "admin")]`, but reads are not role-restricted.
- **Impact**: Any authenticated user (not just admin) can list every rule, including the seeded fraud rules (Program.cs:100-103: `fraud:excessive-amount = totalAmount > 5000`, `fraud:bulk-items = itemCount > 20`, exact country blocklist, etc.). An attacker can read exact thresholds and craft orders that stay just under them, defeating fraud detection entirely.
- **Fix**: Add `[Authorize(Roles = "admin")]` to `List` and `Get`, or split into an internal-only read surface not exposed to regular users. If regular users legitimately need to evaluate rules via `/evaluate`, that endpoint should not echo `Expression`/`Trace` back (see next finding).

## CRITICAL: Expression injection — substituted Inputs are never re-validated, and JSON deserialization breaks the literal-quoting that's supposed to sanitize them
- **File**: src/RulesEngine/RulesEngine.Api/Infrastructure/RulesEvaluator.cs:68,97,181-187; src/RulesEngine/RulesEngine.Api/Application/EvaluateRuleQuery.cs:9-10
- **Issue**: `ValidateExpression` (line 68) checks `rule.Expression` — the stored template — for forbidden tokens *before* `TransformExpression` substitutes caller-supplied `inputs` into it (line 97). The substituted string that actually gets compiled by `DynamicExpressionParser` is never checked. Safety depends entirely on `ToLiteral` (line 181-187) quoting string values. But `EvaluateRuleQuery.Inputs` is `Dictionary<string, object>` bound from a JSON body — System.Text.Json deserializes untyped `object` dictionary values as `JsonElement`, not `bool`/`string`/`int`. In `ToLiteral`, a `JsonElement` matches neither the `bool b` nor `string s` pattern, so it falls to `_ => value.ToString()`. For `JsonValueKind.String`, `JsonElement.ToString()` returns the raw string content **without quotes or escaping** — the caller-controlled string is spliced into the Dynamic LINQ expression as raw, unquoted code instead of a quoted literal.
- **Impact**: Any authenticated caller of `POST /api/v1/rules/evaluate` can pass a string `Inputs` value containing arbitrary Dynamic LINQ syntax (parentheses, operators, method calls on `object`/`string`/`DateTime` which are in `SafeTypeProvider.AllowedTypes`), bypassing the forbidden-token filter entirely since that filter never sees the final expression. At minimum this breaks intended rule semantics (evaluation outcome manipulation on any rule, including fraud rules); depending on what Dynamic LINQ resolves for the allowed types, it's a genuine expression-injection surface. Also: boolean `JsonElement.ToString()` returns `"True"`/`"False"` (capitalized), not the C#-literal `"true"`/`"false"`, silently breaking any rule that takes a boolean input via the HTTP API.
- **Fix**: Use a typed model (or `JsonSerializer` custom converter) so `Inputs` values deserialize to actual `bool`/`double`/`string` before reaching `ToLiteral`. Additionally, re-run `ValidateExpression` (or an equivalent check) against the *substituted* expression, not just the stored template.

### HIGH: Fraud check fails open on any per-rule evaluation error
- **File**: src/RulesEngine/RulesEngine.Api/Infrastructure/FraudCheckConsumer.cs:51-56
- **Issue**: `if (result.IsSuccess && result.Value.Outcome)` treats "rule evaluation failed" (DB blip, parse error, timeout) identically to "rule did not trigger" — no `else` branch logs or escalates a failed evaluation.
- **Impact**: A transient DB hiccup or a bad rule expression silently drops that rule from the fraud score for that order, with no alerting. Fraud detection degrades invisibly under exactly the failure conditions (DB pressure, network blips) that correlate with real incidents.
- **Fix**: Add an `else if (!result.IsSuccess) logger.LogError(...)` branch, and consider failing the whole check closed (block/flag for manual review) rather than silently excluding the rule.

### HIGH: No single fraud rule can independently block a checkout
- **File**: src/RulesEngine/RulesEngine.Api/Infrastructure/FraudCheckConsumer.cs:61 (`riskScore >= 50`), Program.cs:100-103 (each seeded rule worth 25 points)
- **Issue**: Every rule adds exactly 25 points; the fail threshold is 50. `fraud:excessive-amount` (order > $5000) alone never blocks — it always needs a second rule to also trigger.
- **Impact**: A single high-severity signal (e.g., an order for $50,000) passes fraud check unless a second, unrelated rule also fires. This weakens fraud protection for the platform's stated purpose.
- **Fix**: Give rules configurable severity/weight instead of a flat 25, or make specific rules independently blocking.

### HIGH: DB fetch in RulesEvaluator.EvaluateAsync is unprotected — non-cancellation exceptions crash the request
- **File**: src/RulesEngine/RulesEngine.Api/Infrastructure/RulesEvaluator.cs:60-62; src/RulesEngine/RulesEngine.Api/Application/EvaluateRuleQueryHandler.cs:25-49
- **Issue**: `_db.Rules.AsNoTracking().FirstOrDefaultAsync(...)` sits before the method's `try` block (line 72). The handler's own try/catch (lines 25-44) only catches `OperationCanceledException` (line 45).
- **Impact**: Any non-cancellation DB exception (connection drop, Npgsql timeout unrelated to the 5s CancelAfter) on this call propagates uncaught out of MediatR into the controller, bypassing the `Result` pattern the rest of the codebase relies on for typed error responses.
- **Fix**: Wrap the DB fetch in the same try block, or add a catch-all in the handler that maps to `Error.Internal`.

### HIGH: Startup fraud-rule seeding races on multi-instance deploy
- **File**: src/RulesEngine/RulesEngine.Api/Program.cs:96-108
- **Issue**: Check-then-insert (`AnyAsync` then `AddRange`/`SaveChangesAsync`) with a unique index on `Name` (RulesDbContext.cs `HasIndex(r => r.Name).IsUnique()`), and no try/catch around the insert.
- **Impact**: If two instances start concurrently (rolling deploy, multi-region Fly scale), both can pass the `AnyAsync` check before either commits, and the second `SaveChangesAsync` throws an unhandled `DbUpdateException` on the unique constraint, crashing that instance's startup.
- **Fix**: Wrap the seed in a try/catch that swallows the unique-violation case, or use `ON CONFLICT DO NOTHING` via raw SQL, or gate seeding behind a migration instead of app startup.

### HIGH: CreateRuleCommandHandler has no handling for duplicate rule name
- **File**: src/RulesEngine/RulesEngine.Api/Application/RuleCommandHandlers.cs:26-27
- **Issue**: `SaveChangesAsync` isn't wrapped in try/catch; the unique index on `Name` means a duplicate throws `DbUpdateException` straight out of the MediatR pipeline.
- **Impact**: Admin creating a rule with a name that already exists gets an unhandled 500 instead of a clean validation/conflict response.
- **Fix**: Pre-check name uniqueness or catch `DbUpdateException` and translate to `Error.Conflict`.

### MEDIUM: Redundant per-rule DB round trip in FraudCheckConsumer (N+1)
- **File**: src/RulesEngine/RulesEngine.Api/Infrastructure/FraudCheckConsumer.cs:32-34,51
- **Issue**: The consumer already loads full `Rule` rows (id, name, expression) into `rules` at lines 32-34, then calls `evaluator.EvaluateAsync(rule.Id, ...)` per rule, which re-queries the same row by id inside `RulesEvaluator.EvaluateAsync` (RulesEvaluator.cs:60-62).
- **Impact**: Doubles DB round trips per fraud check event (N rules → N+1 extra queries), unnecessary latency/load on the hot checkout path.
- **Fix**: Add an evaluator overload that accepts an already-loaded `Rule`, or evaluate the expression directly from the in-memory list.

### MEDIUM: No optimistic concurrency control on Rule entity
- **File**: src/RulesEngine/RulesEngine.Api/Domain/Rule.cs; src/RulesEngine/RulesEngine.Api/Application/RuleCommandHandlers.cs:39-49,60-66
- **Issue**: `Update`/`Delete` do check-then-mutate with no `RowVersion`/concurrency token.
- **Impact**: Two concurrent admin edits to the same rule silently lose one update (last write wins), with no error surfaced to either caller.
- **Fix**: Add a `byte[] RowVersion` with `IsRowVersion()` in `RulesDbContext`, catch `DbUpdateConcurrencyException` and return `Error.Conflict`.

### MEDIUM: Inputs dictionary has no size bound
- **File**: src/RulesEngine/RulesEngine.Api/Application/EvaluateRuleQueryValidator.cs (only `NotNull()` on Inputs)
- **Issue**: No max key count or value length validation on `Inputs`.
- **Impact**: A caller can submit an oversized dictionary; `TransformExpression` (RulesEvaluator.cs:147-152) does an `OrderByDescending` + full-string scan per entry — a large enough dictionary is a cheap CPU-amplification DoS against a single request.
- **Fix**: Cap `Inputs.Count` (e.g. ≤50) and per-value string length in the validator.

### MEDIUM: Hard delete of Rule, no audit trail
- **File**: src/RulesEngine/RulesEngine.Api/Application/RuleCommandHandlers.cs:58-67

- **Impact**: For a fraud-rules table, losing the exact rule text that decided a past fraud outcome makes incident review/compliance reconstruction impossible.

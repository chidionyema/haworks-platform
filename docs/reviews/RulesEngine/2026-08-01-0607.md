## CRITICAL: Rule-input values from JSON are spliced unquoted/unescaped into a Dynamic LINQ expression that gets compiled and executed — expression injection
- **File**: `src/RulesEngine/RulesEngine.Api/Infrastructure/RulesEvaluator.cs:181-186`, `src/RulesEngine/RulesEngine.Api/Application/EvaluateRuleQuery.cs:8-10`
- **Issue**: `EvaluateRuleQuery.Inputs` is `Dictionary<string, object>` deserialized from a JSON request body. System.Text.Json has no built-in conversion for `object`-typed values — every JSON string/bool/number deserializes into `object` as a boxed `System.Text.Json.JsonElement` (documented .NET behavior; I grepped `src/BuildingBlocks` and found no `JsonConverter`/`ObjectToInferredTypesConverter` registered anywhere that would coerce this — see the two greps I ran confirming zero `AddJsonOptions`/`Converters.Add` calls in the codebase). `ToLiteral` (line 181) pattern-matches on CLR `bool` and `string`:
  ```csharp
  bool b => b ? "true" : "false",
  string s => $"\"{s.Replace("\"", "\\\"")}\"",
  null => "null",
  _ => value.ToString() ?? "null"
  ```
  A `JsonElement` is neither `bool` nor `string`, so both typed branches are dead for every API-sourced input — execution always falls to `value.ToString()`, which returns the **raw, unquoted, unescaped** text of the JSON value. That raw text is substituted directly into `rule.Expression` (`TransformExpression`, line 97) and the resulting string is fed straight into `DynamicExpressionParser.ParseLambda(...).Compile()` (lines 93-100).
- **Impact**: Any authenticated user can call `POST /api/v1/rules/evaluate` (only `[Authorize]`, no role restriction — `RulesController.cs:24`) against any rule ID they can discover (see next finding), supplying a string input whose value is embedded verbatim as source text into a compiled Dynamic LINQ lambda. `SafeTypeProvider` (RulesEvaluator.cs:20-33) only restricts which *named types* can be resolved — it does nothing to stop arbitrary operators, ternaries, or member access already reachable in the spliced text once it's part of the expression source itself, before the type-provider ever gets a say in what identifiers mean. This is textbook expression injection, one level below full RCE.
- **Fix**: Never string-splice caller-controlled values into the expression text. Pass `inputs` as an actual runtime parameter to the compiled lambda (index into the `Dictionary<string,object>` parameter that's already declared but currently unused) instead of textually substituting literals. At minimum, add an `ObjectToInferredTypesConverter`-style `JsonConverter` on the DTO so `Inputs` values are real CLR primitives before they ever reach `ToLiteral`, and add integration test coverage for string-valued inputs through the real HTTP endpoint (currently only numeric `age` is exercised — see Testing finding below, which is exactly what let this ship).

## CRITICAL: Fraud detection fails open — any per-rule evaluation error is silently swallowed as "not triggered"
- **File**: `src/RulesEngine/RulesEngine.Api/Infrastructure/FraudCheckConsumer.cs:49-57`
- **Issue**: 
  ```csharp
  foreach (var rule in rules)
  {
      var result = await evaluator.EvaluateAsync(rule.Id, variables, ct);
      if (result.IsSuccess && result.Value.Outcome)
      {
          triggeredRules.Add(rule.Name);
          riskScore += 25;
      }
  }
  ```
  If `evaluator.EvaluateAsync` returns `Result.Failure` — rule deleted mid-flight, parse error from a bad admin edit, or the internal 5s-style timeout/exception path in `RulesEvaluator.EvaluateAsync` (catch-all at end of that method) — the failure is neither logged nor surfaced. It's treated identically to "rule evaluated to false." There is also no check that `rules` is non-empty; if all fraud rules are deactivated/deleted, the loop simply never runs and every order silently passes.
- **Impact**: In a "mission-critical financial system" (per this repo's own CLAUDE.md), a broken fraud rule, a bad deploy, DB replica lag, or a rules table wiped by the `DeleteRuleCommandHandler` mid-checkout degrades fraud detection to a silent no-op with zero operational visibility — `logger.LogInformation("Fraud check PASSED...")` fires exactly as if everything were healthy.
- **Fix**: Distinguish `Result.Failure` from "did not trigger." Log a warning per failed rule evaluation with the rule ID and error, emit a metric (e.g. `fraud.checks.errors`), and decide an explicit fail-safe policy (fail-closed for a configurable subset of critical rules, or at minimum alert) rather than silently defaulting to pass.

## CRITICAL: Fraud rule definitions (including exact thresholds) are readable by any authenticated non-admin user
- **File**: `src/RulesEngine/RulesEngine.Api/Controllers/RulesController.cs:35-51`
- **Issue**: `Create`/`Update`/`Delete` are `[Authorize(Roles = "admin")]` (lines 53, 64, 77), but `List` (line 35) and `Get` (line 44) carry only the controller-level `[Authorize]` — no role check. `ListRulesQueryHandler`/`GetRuleQueryHandler` return the full `Rule` including `Expression`.
- **Impact**: Any authenticated user (e.g., a customer account, per the checkout/JWT flow documented in this repo's own memory) can `GET /api/v1/rules` and read every fraud rule's exact expression, e.g. `"totalAmount > 500 AND isGuest == true"`, `"totalAmount > 5000"`, `"itemCount > 20"`, `"countryCode == \"XX\" OR countryCode == \"YY\""` (seeded in `Program.cs`). Combined with the risk-score-needs-≥2-rules logic below, an attacker can trivially structure an order (e.g., $499.99, 19 items, non-guest) to stay under every individual threshold and guarantee a pass.
- **Fix**: Restrict `List`/`Get` to `admin` role, or split "read expression" from "read metadata" so non-admin callers never see `Expression`/thresholds.

## HIGH: N+1 queries + no expression-compilation caching on the hot fraud-check path
- **File**: `src/RulesEngine/RulesEngine.Api/Infrastructure/FraudCheckConsumer.cs:33-51`, `src/RulesEngine/RulesEngine.Api/Infrastructure/RulesEvaluator.cs:60-100`
- **Issue**: `FraudCheckConsumer` loads all active fraud `Rule` rows in one query (line 33-34), but then calls `evaluator.EvaluateAsync(rule.Id, ...)` per rule (line 51), and `RulesEvaluator.EvaluateAsync` re-fetches the **same rule row again by ID** from the DB (`_db.Rules.AsNoTracking().FirstOrDefaultAsync(r => r.Id == ruleId...)`) instead of accepting the already-loaded `Rule`. On top of that, every single call does `DynamicExpressionParser.ParseLambda(...).Compile()` from scratch — full text parsing plus IL generation via `Expression.Compile()` — with no caching keyed on rule ID/expression version.
- **Impact**: This runs on every checkout for every active fraud rule: 1 query to list rules + N queries to re-fetch each one individually, plus N full parse+compile cycles, none of which are cheap. Under the k6 soak-test load this repo already runs (`tests/load/`), this is a needless multiplier on both DB load and CPU per checkout.
- **Fix**: Give `IRulesEvaluator` an overload that accepts an already-loaded `Rule`/expression instead of re-querying by ID, and cache the compiled `Func<Dictionary<string,object>, bool>` keyed by `(RuleId, expression hash)`, invalidated on `UpdateRuleCommand`/`DeleteRuleCommand`.

## HIGH: Risk score requires ≥2 triggered rules — a single extreme-risk signal alone never fails the check
- **File**: `src/RulesEngine/RulesEngine.Api/Infrastructure/FraudCheckConsumer.cs:55,61`
- **Issue**: Every triggered rule adds a flat 25 points (`riskScore += 25`), and the failure condition is `triggeredRules.Count > 0 && riskScore >= 50`. Since 25 < 50, no single rule — however severe — can fail a check on its own; it always takes at least two.
- **Impact**: The seeded rule `fraud:excessive-amount` (`totalAmount > 5000`) is meant to catch outsized orders, but a $50,000 guest order that only trips that one rule (e.g., non-guest, normal item count, benign country) scores 25 and **passes**. Severity isn't weighted at all — a single catastrophic signal is treated the same as a single mild one.
- **Fix**: Weight rules by severity (e.g., store a `Weight`/`Severity` on `Rule` instead of a hardcoded `+= 25`), or make single high-severity rules independently sufficient to fail.

## MEDIUM: No handling for concurrent duplicate rule names / lost-update race on rule edits
- **File**: `src/RulesEngine/RulesEngine.Api/Application/RuleCommandHandlers.cs:12-30` (Create), `:32-49` (Update)
- **Issue**: `Rule.Name` has a unique DB index (`RulesDbContext.cs`: `b.HasIndex(r => r.Name).IsUnique()`) but no application-level uniqueness check, and no `try/catch` around `SaveChangesAsync` for either handler. `UpdateRuleCommandHandler` also does a plain read-modify-write with no concurrency token (`Rule` has no `RowVersion`/`xmin` equivalent — consistent with this repo's documented Npgsql 9 xmin removal, but no substitute pessimistic lock was added here either).
- **Impact**: Two concurrent `CreateRuleCommand`s with the same `Name` — one succeeds, the other throws an unhandled `DbUpdateException` (unique violation) that isn't caught anywhere in this handler, surfacing as a raw 500 instead of a domain conflict. Two concurrent `UpdateRuleCommand`s on the same rule silently last-write-wins with no detection, which for a fraud rule is a real business risk (an admin's edit can be silently discarded).
- **Fix**: Catch `DbUpdateException` for the unique index and map to `Error.Conflict`; add a concurrency token to `Rule` and check it in `UpdateRuleCommandHandler`.

## MEDIUM: "SQL injection guard" is misapplied — this pipeline never touches SQL, and the token list is duplicated in two places
- **File**: `src/RulesEngine/RulesEngine.Api/Infrastructure/RulesEvaluator.cs:38-46` (comment: `// SQL injection guard: block common injection patterns in expressions`), duplicated verbatim as `ExpressionRules.ForbiddenTokens` in `src/RulesEngine/RulesEngine.Api/Application/RuleCommandValidators.cs:5-13` (comment: `// Forbidden SQL injection tokens — kept in sync with RulesEvaluator`)
- **Issue**: Rule expressions are never used in raw SQL anywhere in this file — they're parsed and compiled as Dynamic LINQ. Blocking `DROP`/`SELECT`/`UNION`/etc. does nothing to prevent the actual expression-injection vector described in the first CRITICAL finding, and gives a false sense of security. The list also exists in two files that must be manually kept in sync (comment literally says "kept in sync" — there's no shared constant enforcing that).
- **Impact**: Reviewers/on-call engineers may reasonably assume this guard defends against expression injection because it's labeled a security control; it doesn't, and the actual injection path (JsonElement → unquoted literal splice) is completely orthogonal to any of these tokens.
- **Fix**: Remove the misleading "SQL injection" framing, extract the token list to one shared constant referenced by both files, and pair with the structural fix (parameterized evaluation instead of text splicing) from the first CRITICAL finding — token blocklists are not a substitute for that.

## LOW: `TransformExpression`'s `NOT`/`AND`/`OR` replacement is whitespace-fragile
- **File**: `src/RulesEngine/RulesEngine.Api/Infrastructure/RulesEvaluator.cs:139-143`
- **Issue**: `.Replace(" NOT ", " !", ...)` (and `AND`/`OR`) requires a literal space on both sides. An expression starting with `NOT isGuest` (no leading space) or written as `NOT(isGuest)` won't be rewritten, and will fail to parse as Dynamic LINQ.
- **Impact**: Legitimate admin-authored expressions using boundary `NOT`/`AND`/`OR` fail with a confusing `ParseError` rather than evaluating correctly. Not a security issue (caught by the try/catch), just a reliability/UX gap for rule authors.
- **Fix**: Use a regex with word-boundary matching (`\bNOT\b`) instead of literal space-delimited `Replace`.

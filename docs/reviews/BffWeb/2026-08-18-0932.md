## CRITICAL: Checkout accepts client-supplied prices with no server-side re-pricing
- **File**: `src/BffWeb/BffWeb.Api/Controllers/CheckoutController.cs:96-113`, confirmed downstream at `src/CheckoutOrchestrator/CheckoutOrchestrator.Application/Commands/StartCheckoutCommand.cs:31-72`
- **Issue**: `CheckoutController.Start` builds the request to checkout-svc entirely from the browser-supplied `CheckoutRequest` — `totalAmount`, `unitPriceCents` per item, even `productName` — and forwards it verbatim. `StartCheckoutCommand`'s handler publishes `CheckoutInitiatedEvent` with `request.TotalAmountCents`/`request.Items` unchanged; its validator only checks `TotalAmountCents > 0` / `UnitPriceCents > 0`, never re-prices against Catalog/Pricing. `PaymentAmountMismatchEvent` only fires if what Stripe actually charged differs from the (already-tampered) total the saga itself set — it can't catch a client who lowers `unitPriceCents` before the session is created, because Stripe is told to charge exactly that lowered price.
- **Impact**: Any authenticated user can POST arbitrary `unitPrice`/`totalAmount` values and complete a real order (and a real Stripe charge) at a self-chosen price. This is a live price-tampering / financial-fraud path in a payments-adjacent BFF.
- **Fix**: BFF (or checkout-svc) must re-price every line item from catalog-svc's authoritative price before publishing `CheckoutInitiatedEvent`; reject if client total doesn't match server-computed total.

## HIGH: AI endpoints reachable anonymously with no rate-limit tier
- **File**: `src/BffWeb/BffWeb.Api/Controllers/AiController.cs:19-40`
- **Issue**: `SemanticSearch` and `ChatMessage` have no `[Authorize]` (unlike `Recommendations`/`GenerateContent` in the same controller, which do), and none of the four AI actions use `[EnableRateLimiting("expensive")]` — only the process-wide 120 req/min global IP limiter applies.
- **Impact**: Unauthenticated callers can drive real LLM (Claude) spend on `ai-svc` at up to the global limiter's rate, with no per-endpoint throttle — a cost-abuse/DoS vector distinct from ordinary passthrough REST calls.
- **Fix**: Require `[Authorize]` consistently or explicitly document anonymous search as intended, and add `[EnableRateLimiting("expensive")]` (or a dedicated AI tier) to all four actions.

## HIGH: Rate limiter partitions by `RemoteIpAddress` with no ForwardedHeaders middleware
- **File**: `src/BffWeb/BffWeb.Api/Program.cs:44-52` (GlobalLimiter), `:56-65` (`authenticated`/`expensive` policies)
- **Issue**: `grep -rn "ForwardedHeaders"` across `src/BuildingBlocks` and `src/BffWeb` returns nothing — no `UseForwardedHeaders()`/`ForwardedHeadersOptions` anywhere. All three rate-limit partitions key on `ctx.Connection.RemoteIpAddress`.
- **Impact**: If the BFF sits behind any proxy/edge that doesn't preserve the original client's IP at the TCP layer, every visitor collapses into one shared bucket — one abusive client exhausts the limit for everyone, or (worse) the limiter becomes a no-op relative to per-user abuse. I can't confirm Fly.io's exact proxy behavior for this app without checking Fly's runtime docs, but the missing middleware is itself the gap regardless of the current topology.
- **Fix**: Add `app.UseForwardedHeaders(...)` configured for Fly's proxy (or confirm Fly passes the real client IP at Kestrel and document why it's safe to skip).

## MEDIUM: BffServiceTokenProvider leaks an unhandled TimeoutException
- **File**: `src/BffWeb/BffWeb.Infrastructure/Authentication/BffServiceTokenProvider.cs:34-35`
- **Issue**: `if (!await _lock.WaitAsync(TimeSpan.FromSeconds(15), ct)) throw new TimeoutException(...)` sits *before* the surrounding `try/catch`, so it isn't caught by the method's own `catch (Exception ex) { ...; return null; }`. Every other failure path in this method returns `null` (the documented contract `CheckoutController.cs:104` relies on: `if (!string.IsNullOrEmpty(svcToken))`).
- **Impact**: Under lock contention (concurrent checkout starts during a token refresh), the caller gets an unhandled `TimeoutException` instead of a graceful "no service token" fallback — a raw 500 to the browser during checkout.
- **Fix**: Move the `WaitAsync` timeout check inside the try, or catch `TimeoutException` and return `null` like the rest of the method.

## MEDIUM: JourneyScheduler writes unbounded synthetic data to production forever
- **File**: `src/BffWeb/BffWeb.Api/Demo/JourneyScheduler.cs:52-91`, registered unconditionally at `Program.cs:189`
- **Issue**: Runs in every environment including production, firing a real `place-order-saga` (creates a real Checkout/Order row) and a real `occ-race` (concurrently PUTs the same demo product's inventory) every 20 seconds, indefinitely. No cleanup/retention job is referenced anywhere in the reviewed files.
- **Impact**: Continuous, unbounded row growth in Orders/Checkout tables (~4,300 synthetic sagas/day) and repeated live mutation of the demo product's stock — inflates DB size and demo-metrics noise over time, and risks colliding with the platform's own "unbounded saga terminal state row growth" anti-pattern (`MEMORY.md` item 14).
- **Fix**: Either scope JourneyScheduler to Development/Staging, or add a retention/cleanup sweep for its synthetic Checkout/Order rows.

## LOW: AI controller actions accept an untyped `object` body
- **File**: `src/BffWeb/BffWeb.Api/Controllers/AiController.cs:24,42,62,74`
- **Issue**: All four actions bind `[FromBody] object body` — no DTO, no `[Required]`/size validation — and forward the raw JSON straight to `ai-svc`.
- **Impact**: No input-shape validation at the API boundary; malformed or oversized payloads are only caught (or not) by `ai-svc` itself.
- **Fix**: Define request DTOs for each AI action, even if they're thin passthrough records (matches the pattern already used by `CheckoutRequest`).

#### HIGH: AuditWriter must dead-letter after MaxRetries on persistent Postgres failure
- **For**: `src/Audit/Audit.Infrastructure/Persistence/AuditWriter.cs:148-172`
- **Type**: Unit (requires refactor to inject a fakeable DB accessor) or Integration (force a COPY failure, e.g. malformed jsonb / connection killed mid-batch)
- **Why**: `WriteBatchAsync` catches `PostgresException`, re-queues rows below `MaxRetries=3`, and silently drops rows at/above the limit (`AuditWriter.cs:156-162`). Nothing proves the drop actually happens, or that requeued rows are eventually retried and succeed. A regression here (e.g. off-by-one, infinite requeue loop) would silently lose audit rows in production with no test catching it.
- **Skeleton**:
```csharp
[Fact]
public async Task WriteAsync_DropsRow_AfterMaxRetriesExceeded()
{
    // Arrange: seed a scope whose AuditDbContext connection is closed/invalid
    // so every COPY attempt throws PostgresException.
    using var scope = _factory.Services.CreateScope();
    var writer = scope.ServiceProvider.GetRequiredService<IAuditWriter>();
    var loggerProbe = new TestLoggerSink(); // capture LogError calls

    var row = new AuditRow(DateTimeOffset.UtcNow, "TestEvent", "order", "bad-id",
        null, null, null,
        JsonSerializer.SerializeToElement(new { }),
        JsonSerializer.SerializeToElement(new { }));

    // Act
    await writer.WriteAsync(row, CancellationToken.None);
    await writer.FlushAsync(CancellationToken.None);

    // Assert: row was retried exactly MaxRetries-1 times then dropped —
    // verify via captured "dropping audit row after 3 failed attempts" log,
    // and assert it never landed in audit.audit_events.
    loggerProbe.Errors.Should().Contain(e => e.Contains("dropping audit row after"));
}
```

#### MEDIUM: Partition/query tests hand-create an unschemed duplicate `audit_events` table
- **File**: `tests/Audit/Audit.Integration/PartitionRolloverTests.cs:29`, `tests/Audit/Audit.Integration/QueryApiTests.cs:53`
- **Violation**: Both tests run `CREATE TABLE IF NOT EXISTS audit_events (...) PARTITION BY RANGE (...)` with **no schema qualifier**, creating a second table in the connection's default search-path schema (`public`), separate from the real `audit.audit_events` partitioned table the migration (`20260510144352_AddAuditEventsPartitioned.cs`) already created via `AuditWebAppFactory.EnsureSchemaAsync()`. `PartitionRolloverTests` then queries `pg_inherits`/`pg_class` filtering only on `relname = 'audit_events'` with no `nspname` (schema) filter, which is ambiguous once both tables exist in the shared reused container — this is exactly the "testing a rebuilt mock instead of real behavior" anti-pattern the platform rules exist to prevent.
- **Fix**: Delete the manual `CREATE TABLE` block in both files (the schema/table already exists via `AuditWebAppFactory.InitializeAsync → EnsureSchemaAsync`); qualify any `pg_inherits` verification query with `parent.relnamespace = 'audit'::regnamespace`.

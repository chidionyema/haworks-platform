## Missing Tests (priority order)

#### HIGH: Concurrent CreateMerchant race is untested and violates the Logical Idempotency Law
- **For**: `CreateMerchantCommand.cs:56-64` — catches `DbUpdateException`/`PostgresException 23505` after `_publishEndpoint.Publish` already staged an outbox row in the same `SaveChangesAsync`
- **Type**: Unit + architecture concern
- **Why**: CLAUDE.md Law 3 explicitly forbids relying on unique-index violation catches for concurrency — "it poisons the DbContext and breaks the MassTransit Outbox." Here a duplicate owner/slug race throws mid-`SaveChangesAsync`, after the outbox insert was already added to the same context — the `DbUpdateException` catch converts it to a friendly error, but the poisoned `DbContext` scenario (partial write state, disposed transaction) is never verified to behave safely. No test proves the outbox message is NOT partially persisted on this path.
- **Skeleton**:
```csharp
[Fact]
public async Task Handle_concurrent_duplicate_slug_insert_throws_and_does_not_leave_outbox_row()
{
    var context = CreateInMemoryContext(); // or real Postgres via SharedTestPostgres for a true 23505
    var ownerId = Guid.NewGuid();
    var slug = "taken-slug";
    context.Merchants.Add(MerchantProfile.Create(Guid.NewGuid(), "Existing", slug));
    await context.SaveChangesAsync();

    var publishMock = new Mock<IPublishEndpoint>();
    var handler = new CreateMerchantCommandHandler(context, publishMock.Object);
    var command = new CreateMerchantCommand(ownerId, "New Shop", slug);

    var act = async () => await handler.Handle(command, CancellationToken.None);

    await act.Should().ThrowAsync<InvalidOperationException>()
        .WithMessage("*already in use*");
    // Assert no orphaned Merchant row from the failed insert
    (await context.Merchants.CountAsync(m => m.Slug == slug)).Should().Be(1);
}
```
Recommend replacing the pre-check `AnyAsync` + catch-23505 pattern with the platform's `FOR UPDATE`-on-business-key idempotency journal pattern used elsewhere, per Law 3.

#### HIGH: SetOperatingHoursCommand — validator and handler both untested
- **For**: `SetOperatingHoursCommand.cs:23-38` (validator: max-7 rule, duplicate-day rule, open<close-with-midnight-exception rule) and `:52-77` (handler: not-found, forbidden, remove-then-replace)
- **Type**: Unit
- **Why**: This is the most complex validation logic in the service (three chained rules, a special-cased 00:00/00:00 "24h" sentinel) and it ships with zero tests. [Fact]
public async Task Handle_replaces_existing_hours_entirely()
{
    var context = CreateInMemoryContext();
    var ownerId = Guid.NewGuid();
    var merchant = MerchantProfile.Create(ownerId, "Shop", "shop");
    context.Merchants.Add(merchant);
    context.OperatingHours.Add(OperatingHours.Create(merchant.Id, 1, TimeSpan.FromHours(8), TimeSpan.FromHours(16)));
    await context.SaveChangesAsync();

    var handler = new SetOperatingHoursCommandHandler(context);
    var newHours = new List<OperatingHourDto> { new(DayOfWeek.Tuesday, TimeSpan.FromHours(9), TimeSpan.FromHours(17), true) };
    var result = await handler.Handle(new SetOperatingHoursCommand(merchant.Id, ownerId, newHours), CancellationToken.None);

    result.IsSuccess.Should().BeTrue();
    var stored = await context.OperatingHours.Where(h => h.MerchantId == merchant.Id).ToListAsync();
    stored.Should().ContainSingle(h => h.DayOfWeek == (int)DayOfWeek.Tuesday);
}

## Missing Tests (by priority)

#### HIGH: WebhooksController.Ses — no coverage at all
- **For**: `WebhooksController.cs:Ses` (SNS signature validation, SubscriptionConfirmation, Notification parse, exception→400)
- **Type**: Unit (controller) + Integration
- **Why**: This is an unauthenticated (`[AllowAnonymous]`) endpoint whose only gate is SNS signature verification. An untested signature check on a public endpoint is a zero-trust/security gap — a bug here means either forged webhooks are accepted or legitimate ones are rejected silently.
- **Skeleton**:
```csharp
[Fact]
public async Task Ses_InvalidSnsSignature_Returns400()
{
    var payload = BuildSnsPayload(type: "Notification", validSignature: false);
    _sut.Request.Body = new MemoryStream(Encoding.UTF8.GetBytes(payload));
    var result = await _sut.Ses(CancellationToken.None);
    result.Should().BeOfType<BadRequestObjectResult>();
    _publishMock.Verify(p => p.Publish(It.IsAny<NotificationWebhookValidatedEvent>(),
        It.IsAny<Action<PublishContext>>(), It.IsAny<CancellationToken>()), Times.Never);
}
```
*(SNS signature verification requires signing a real message with a test cert — build a small SNS-message-signer test helper, or wrap `Message.ParseMessage`/`IsMessageSignatureValid` behind an injectable seam so it can be mocked.)*

#### HIGH: UpdateNotificationStatusFromWebhookHandler — most branches untested
- **For**: `UpdateNotificationStatusFromWebhookCommand.cs:Handle` (SendGrid/Twilio branches, unknown-message-id no-op, `DbUpdateException` 23505 retry path, already-terminal guards)
- **Type**: Unit
- **Why**: The duplicate-suppression retry path (`ClearChangeTracker` + reload + status-only re-apply) is genuinely tricky concurrency-adjacent logic and currently has zero coverage — a regression here would silently drop the status update on every bounce race.
- **Skeleton**:
```csharp
[Fact]
public async Task Handle_DuplicateSuppressionConstraint_ClearsTrackerAndRetriesStatusOnly()
{
    var notification = CreateSentNotification();
    _repositoryMock.Setup(r => r.GetByProviderMessageIdAsync("msg-1", It.IsAny<CancellationToken>()))
        .ReturnsAsync(notification);
    _repositoryMock.SetupSequence(r => r.SaveChangesAsync(It.IsAny<CancellationToken>()))
        .ThrowsAsync(new DbUpdateException("dup", new PostgresException("dup", "E", "E", "23505")))
        .ReturnsAsync(1);
    var cmd = new UpdateNotificationStatusFromWebhookCommand("SES", "msg-1", "Bounce", "{}");
    await _sut.Handle(cmd, CancellationToken.None);
    _repositoryMock.Verify(r => r.ClearChangeTracker(), Times.Once);
    _repositoryMock.Verify(r => r.SaveChangesAsync(It.IsAny<CancellationToken>()), Times.Exactly(2));
}

[Fact]
public async Task Handle_UnknownProviderMessageId_ReturnsSuccessWithoutSideEffects()
{
    _repositoryMock.Setup(r => r.GetByProviderMessageIdAsync("nope", It.IsAny<CancellationToken>()))
        .ReturnsAsync((Notification?)null);
    var result = await _sut.Handle(new UpdateNotificationStatusFromWebhookCommand("SES", "nope", "Delivery", "{}"), CancellationToken.None);
    result.IsSuccess.Should().BeTrue();
    _repositoryMock.Verify(r => r.SaveChangesAsync(It.IsAny<CancellationToken>()), Times.Never);
}
```

## Test Optimization Violations

#### HIGH: `NotificationsWebAppFactory.ConfigureWebHost` uses `ConfigureServices`, not `ConfigureTestServices`
- **File**: `tests/Notifications/Notifications.Integration/NotificationsWebAppFactory.cs` (the `builder.ConfigureServices(services => {...})` block that strips `IEmailProvider` and wires the MassTransit test harness)
- **Violation**: Platform rule "MUST use ConfigureTestServices not ConfigureServices". `ConfigureTestServices` is guaranteed to run *after* `Program`'s own service registrations so overrides win; plain `ConfigureServices` has no such ordering guarantee against the entry point's builder, so the `IEmailProvider` removal and MassTransit harness swap are order-dependent by accident, not by design.
- **Fix**: `builder.ConfigureTestServices(services => { ... })` instead of `builder.ConfigureServices(...)`.

#### MEDIUM: `PipelineTests.PollUntilStatusAsync` uses `Task.Delay(100)` in a manual loop
- **File**: `tests/Notifications/Notifications.Integration/PipelineTests.cs:PollUntilStatusAsync`
- **Violation**: Platform rule "MUST use TestWait.Until() instead of Task.Delay() for polling" — `BuildingBlocks.Testing.TestWait.Until` already exists in this repo for exactly this pattern.
- **Fix**:
```csharp
await TestWait.Until(async () =>
{
    await using var scope = factory.Services.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<NotificationsDbContext>();
    var status = await db.Notifications.AsNoTracking().Where(n => n.Id == id)
        .Select(n => (NotificationStatus?)n.Status).FirstOrDefaultAsync();
    return status == expected;
}, timeout: TimeSpan.FromSeconds(30), because: $"notification {id} should reach {expected}");
```

#### LOW: Misleading test name in `WebhooksControllerTests`
- **File**: `tests/Notifications/Notifications.Unit/Webhooks/WebhooksControllerTests.cs:SendGrid_ValidPayload_PublishesEvents`
- **Violation**: Not a Testcontainers/CI rule violation, but a naming/quality defect — the test name claims a happy-path publish assertion, the body asserts a 400 from a deliberately invalid signature. `Method_Scenario_ExpectedResult` naming convention is broken.
- **Fix**: Rename to `SendGrid_InvalidSignature_Returns400`, and add a separate genuinely-happy-path test (see HIGH finding above).

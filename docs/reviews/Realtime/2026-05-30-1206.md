## CRITICAL: Deduplication Logic is Inverted - Data Corruption Risk

### CRITICAL: Redis deduplication logic completely broken
- **File**: src/Realtime/Realtime.Api/Infrastructure/Persistence/RedisInboxService.cs:28-29
- **Issue**: `SetAddAsync` returns `true` when item is NEW (added), `false` when already exists. Code treats `alreadySeen = true` as "skip because duplicate", but it means the opposite.
- **Impact**: NEW messages are skipped, DUPLICATE messages are processed. Complete deduplication failure causing message loss and duplicates.
- **Fix**: Change `if (!alreadySeen)` to `if (alreadySeen)` - skip when the item was successfully added (new).

### CRITICAL: Redis transaction failures silently ignored
- **File**: src/Realtime/Realtime.Api/Infrastructure/Persistence/RedisInboxService.cs:47
- **Issue**: `await tran.ExecuteAsync()` result is ignored. Transaction could fail, leaving inbox in inconsistent state.
- **Impact**: Messages could be stored in dedup set but not in inbox list, or vice versa, causing permanent inconsistency.
- **Fix**: Check `ExecuteAsync()` result and handle failure cases.

# Realtime Service — Architectural Review

## CRITICAL: Idempotency is broken — messageId regenerated on every retry, defeating dedup
- **File**: src/Realtime/Realtime.Api/Application/Notifications/SendNotificationCommandHandler.cs:28
- **Issue**: `var messageId = Guid.NewGuid();` is generated fresh inside `Handle()`, then used as the dedup key in `RedisInboxService.StoreMessageAsync` (RedisInboxService.cs:28, `SetAddAsync(dedupKey, messageId.ToString())`). MassTransit redelivers `OrderStatusChanged` on transient failure via `RealtimeConsumerDefinition`'s `UseMessageRetry` (1s/5s/15s). Each redelivery re-enters `Consume` → `Handle` → a **new** `Guid.NewGuid()`. `context.MessageId` (the event's stable ID) is never used.
- **Impact**: The Redis dedup set (`SetAddAsync`) can never see a repeat ID in practice, so it's dead code for its stated purpose ("If messageId was already stored, this is a no-op (idempotent)" — IInboxService.cs:20). Every retry stores a *new* inbox entry and pushes a *second* live SignalR notification. A user gets duplicate order-status notifications on any transient failure (Redis blip, SignalR send failure, pod restart mid-handler).
- **Fix**: Derive `messageId` deterministically from the source event, e.g. pass `context.MessageId ?? NewId.NextGuid()` from `OrderStatusChangedConsumer` through `SendNotificationCommand`, or hash `(OrderId, NewStatus, ChangedAt)`. Add a `MessageId` field to `SendNotificationCommand` instead of generating it inside the handler.

## CRITICAL: Unit test files reference method overloads that don't exist — project will not compile
- **File**: tests/Realtime/Realtime.Unit/Infrastructure/RedisInboxServiceTests.cs:50, :95 (approx.)
- **Issue**: `await _sut.StoreMessageAsync(userId, message);` and `await _sut.AcknowledgeMessagesAsync(userId);` call 2-arg / 1-arg overloads. The actual interface (IInboxService.cs) requires `StoreMessageAsync(Guid, Guid, string, object, CancellationToken = default)` (messageId and messageType have no defaults) and `AcknowledgeMessagesAsync(Guid, int, CancellationToken = default)` (deliveredCount has no default). Same problem in `SendNotificationCommandHandlerTests.cs:46-49`, which `Verify`s `StoreMessageAsync(command.UserId, It.IsAny<object>(), It.IsAny<CancellationToken>())` — a 3-arg signature that doesn't exist on the real interface.
- **Impact**: `dotnet build`/`dotnet test` on `Realtime.Unit` fails outright (CS1501/CS7036). Per project rules ("MANDATORY: Pre-Push Verification"), this means either these tests were never actually run against current code, or the dedup/messageType fixes (C1/C2/H1/H2 comments in source) shipped with zero passing coverage. Also `RedisInboxServiceTests` asserts key `$"inbox:{userId}"` (line ~66) vs actual `InboxKey()` → `$"realtime:inbox:{userId}"` (RedisInboxService.cs, `InboxKey`), so even a fixed signature would fail the assertion.
- **Fix**: Rewrite both test files against the current `IInboxService`/`RedisInboxService` signatures (pass explicit `messageId`, `messageType`, `deliveredCount`; fix key prefix), and add a test exercising the dedup path (same `messageId` twice → second `StoreMessageAsync` is a no-op, no second `LPUSH`).

## HIGH: One malformed inbox entry permanently blocks flush for that user
- **File**: src/Realtime/Realtime.Api/Infrastructure/Persistence/RedisInboxService.cs:66
- **Issue**: `JsonSerializer.Deserialize<InboxEnvelope>((string)items[i]!)` (and the `envelope.DataJson` deserialize at line 70) has no try/catch. A single corrupt or schema-incompatible entry (e.g. a future deploy changes `InboxEnvelope`'s shape) throws `JsonException`, which propagates out of `GetMessagesAsync` into `NotificationHub.OnConnectedAsync` (NotificationHub.cs:39) before `AcknowledgeMessagesAsync` is ever called.
- **Impact**: The connection attempt fails, and because messages are only trimmed *after* a fully successful flush, the poison entry sits in the list for up to 7 days (`InboxTtlDays`), breaking every future login/reconnect for that user until it naturally expires or is manually purged. One bad write becomes a self-inflicted denial of push notifications.
- **Fix**: Wrap the per-item deserialize in try/catch, `_logger.LogError` and skip the bad entry (and optionally have `AcknowledgeMessagesAsync` still trim past it) rather than letting one entry poison the whole read.

## HIGH: Concurrent connections for the same user can lose newly-arrived messages
- **File**: src/Realtime/Realtime.Api/Infrastructure/SignalR/NotificationHub.cs:39-60 and RedisInboxService.cs:88-95
- **Issue**: `GetMessagesAsync` is a peek (no removal). Two simultaneous `OnConnectedAsync` invocations for the same user (multi-tab/multi-device — a normal case for a notification hub) both read the same N messages, then both call `AcknowledgeMessagesAsync(userId, N)`. `AcknowledgeMessagesAsync` re-queries `ListLengthAsync` fresh each call: if `currentLength <= deliveredCount` it does `KeyDeleteAsync` (full delete), not a bounded trim.
- **Impact**: If a genuinely new message arrives between the two acks (pushed to the now-shorter list), the second connection's ack can compute `currentLength <= deliveredCount` again and issue `KeyDeleteAsync`, wiping out the just-arrived message before it's ever delivered. Silent notification loss, no error surfaced anywhere.
- **Fix**: Make ack conditional on the actual message IDs delivered (e.g. `LREM` the specific serialized entries, or compare-and-trim only entries whose envelope IDs were in the delivered set) instead of a blind count-based `LTRIM`/`DEL`.

## MEDIUM: Dedup key TTL is shorter than the inbox TTL, allowing duplicate re-store
- **File**: src/Realtime/Realtime.Api/Infrastructure/Persistence/RedisInboxService.cs:9-10, 45-46
- **Issue**: `DedupTtlDays = 3` while `InboxTtlDays = 7`. If the same `messageId` is redelivered after the dedup key expires (day 4-7) — e.g. a DLQ replay or manual reprocessing job — `SetAddAsync` succeeds again and the message is re-stored/re-pushed, even though the original inbox entry may still be sitting there.
- **Impact**: Duplicate notification delivered for events reprocessed 3-7 days later. Low likelihood given MassTransit's short retry intervals, but the two TTLs being inconsistent is itself a maintainability trap — this is compounded by the CRITICAL messageId bug above, since fixing that makes this TTL mismatch the *actual* remaining duplicate-risk window.
- **Fix**: Set `DedupTtlDays` ≥ `InboxTtlDays` (or just reuse one constant) so dedup coverage never expires before the message itself does.

## MEDIUM: No size bound on notification payload before it's written to Redis
- **File**: src/Realtime/Realtime.Api/Application/Notifications/SendNotificationCommandValidator.cs:10, RedisInboxService.cs:38-39
- **Issue**: `SendNotificationCommandValidator` only checks `Data` is not null. `RedisInboxService.StoreMessageAsync` serializes `message` and `envelope` unconditionally into an `LPUSH` value with no size cap.
- **Impact**: Any producer (or future consumer) that stuffs a large object into `Data` grows the Redis list value unbounded per entry, up to 1000 entries per user — a memory/scalability risk with no validation gate to catch it early.
- **Fix**: Add a max-serialized-size check in the validator or in `StoreMessageAsync` (reject/log and drop rather than store oversized payloads).

## LOW: No health check for the RabbitMQ/MassTransit bus
- **File**: src/Realtime/Realtime.Api/DependencyInjection.cs:66-68
- **Issue**: `AddHealthChecks()` only registers `RedisHealthCheck` under the `ready` tag. There's no check for MassTransit/RabbitMQ connectivity even though the service's core function (relaying `OrderStatusChanged` → notification) depends on it.
- **Impact**: `/ready` can report healthy while the RabbitMQ consumer is disconnected, silently dropping order-status notifications with no operational signal.
- **Fix**: Add MassTransit's bus health check (`services.AddHealthChecks().AddCheck<BusHealthCheck>(...)` or the standard `AddMassTransitHealthCheck`) tagged `ready`.

## LOW: CancellationToken not propagated from the Hub into inbox reads/sends
- **File**: src/Realtime/Realtime.Api/Infrastructure/SignalR/NotificationHub.cs:39, 55
- **Issue**: `_inboxService.GetMessagesAsync(userId)` and `Clients.Caller.SendAsync("ReceiveNotification", msg)` don't pass `Context.ConnectionAborted`, even though both accept a `CancellationToken`.
- **Impact**: A disconnect mid-flush can't be observed by the awaited calls; wasted work continues until it completes on its own instead of being cancelled promptly.
- **Fix**: Pass `Context.ConnectionAborted` through both calls.

## LOW: No prefetch/concurrency bound on the OrderStatusChanged endpoint
- **File**: src/Realtime/Realtime.Api/Infrastructure/Messaging/RealtimeConsumerDefinition.cs:15-21
- **Issue**: Only `UseMessageRetry` is configured; no `ConcurrentMessageLimit`/prefetch count on the receive endpoint.
- **Impact**: A burst of order-status events (e.g. bulk backfill) can flood the consumer with unbounded concurrency, each spawning a SignalR send.
- **Fix**: Set an explicit `endpointConfigurator.ConcurrentMessageLimit = N` matched to Redis/SignalR backplane capacity.

## Summary
- **Findings**: 2 CRITICAL, 2 HIGH, 3 MEDIUM, 3 LOW (10 total)
- **Top 3 most urgent**:
  1. Idempotency is not actually enforced — `messageId` is regenerated on every MassTransit retry, so duplicate notifications ship on any transient failure (SendNotificationCommandHandler.cs:28).
  2. The unit test suite for this service does not compile against the current `IInboxService` interface — there is effectively zero verified coverage of the dedup/inbox logic.
  3. A single malformed Redis entry can permanently block inbox flush for a user for up to 7 days (RedisInboxService.cs:66).
- **Overall service health: 4/10.** The design (Redis-backed inbox, TTL-based dedup, at-least-once get-then-ack, retry policy) is architecturally sound on paper, but the one property it depends on — a stable `messageId` across retries — is violated at the source, and the test suite that should have caught this doesn't build.
